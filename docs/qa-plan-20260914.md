## E. F4 附件上传 · 示范评审(走完四步流程)

### ① 现状与自评提问

现状:app/web 三入口(相册/相机/文件);分块 768KB base64 编码+进度回调;单 JSON 请求直传 `POST /api/sessions/:id/files`;server 50MB 上限+文件名净化;app 有 2 次退避重试,web 原本无。

评审视角的挑战性问题:
1. **base64 膨胀 33%**:50MB 文件 → 66MB+ 的 JSON 体,且 `dataB64` 全量字符串在内存里再拼一份——移动端浏览器内存峰值双份,会不会 OOM?→ 会,这是当前最大的结构性弱点。
2. **"分块"只存在于编码层**:进度回调按块报,但网络层是单请求——失败一次,全部重来,分块没有带来断点续传能力。
3. web 无重试(app 有)→ 弱网下成功率低于 app。→ **已修(本轮)**
4. 上传中无法取消、切后台无提示。
5. 并发同名文件靠 `Date.now()` 前缀兜底——同一毫秒并发会互相覆盖(概率极低,记录)。

### ② 业界调研(GitHub/官方)

- **分块+可续传结合**是共识:每块独立请求、逐块重试、按文件哈希询问服务端"已有哪些块"再续传([Uploadcare 指南](https://uploadcare.com/blog/handling-large-file-uploads/)、[Stackademic 大文件上传系统设计](https://blog.stackademic.com/when-uploading-is-no-longer-just-upload-how-we-designed-large-file-uploads-0eb551c62d0f))。
- **tus 协议 + Uppy** 是跨端可续传的成熟开源方案([tus.io](https://tus.io/)、[Uppy docs](https://uppy.io/docs/tus/)),但要求服务端实现 tus 协议。
- **S3 Multipart + presigned URL** 适合对象存储后端(我们不是)。
- 代理/CDN 会干扰分块协议(Cloudflare + tusDotNet 踩坑记录)——我们的局域网直连无此问题。

### ③ 对比结论

| 维度 | 业界方案 | 我们 | 差距 |
|---|---|---|---|
| 网络层 | 每块独立请求 | 单请求(base64 JSON) | 🔴 结构性 |
| 失败恢复 | 每块重试+断点续传 | app 重试 2 次;web 本轮补齐 | 🟡 web 已补齐重试 |
| 内存 | 流式/每块读 | 全量读+全量 base64 字符串 | 🟡 移动端大文件风险 |
| 协议依赖 | tus 需服务端支持 | 自有 JSON 协议 | 无需引入(过度设计) |
